# MAT-109: Ori Eval workflow fit for Kyber

Status: limited synthetic pilot; product decision proposed, **not a production eval integration**. Date: 2026-10-09.

## Decision

Offer Ori Eval initially as a documented, opt-in **external evaluation job** for comparing candidate OpenRouter models on sanitized Kyber-like tasks. Do not add a Kyber API, CRD, console action, or background job under MAT-110 yet. Ori Eval runs its own temporary `ori` harness; it does not exercise a persistent Kyber Claude, Codex, or Hermes agent, its channels, hooks, tools, identity, or restart path. Present its results as screening evidence only. A later Kyber integration needs a separate, consented execution and data-retention design plus a live harness conformance result from MAT-106.

The job must use an isolated workspace and an OpenRouter key with a provider-enforced spend limit. The current injected key reports `limit: null`; no further paid pilot or full sweep should run on it until a small cap is configured. A local assertion such as `toCostAtMost` observes cost **after** a request and is not a spending control.

## Evidence

- Read the current [Ori Eval guide](https://openrouter.ai/docs/guides/ori/eval) and the bundled `ori eval docs sdk`, `running`, and `lifecycle` references in Ori CLI `0.15.6+4855f79` (same pinned binary and checksum recorded in [MAT-106 PR #311](https://github.com/matty-v/kyber/pull/311)). `ori eval --list --allow-no-key` and `--dry-run --hermetic --no-history` discovered four synthetic tests without model calls. Bun `1.4.2` was installed under `/tmp` only for this pilot; neither binary nor an API key entered the repo.
- The opt-in fixture had two synthetic cases: return a `clamp` JavaScript function, and apply a fictional 30-day refund policy. It compared `cohere/north-mini-code:free` with `nvidia/nemotron-3.5-lightning:free`, requested `reasoning.effort=none` and at most 256 output tokens, and required completion, a deterministic phrase, elapsed time under 90 seconds, and reported cost under $0.001. It used `pilotCases`; `--pilot 1` sampled the coding case for each model. Both sampled cases passed, with observed durations 3.19s and 1.79s. This sample says nothing about the support case or relative model quality. No tools or Kyber channels were exercised.
- `--pilot 1 --hermetic --no-history --features <empty directory>` excluded workspace instructions and skills while retaining Ori's own skills. The pilot result identified the execution harness as `ori`, not Kyber's persistent runtime. `--no-history` suppressed the summary history, but the temporary workspace still held Ori session history; a production job must govern that data and delete it after artifact extraction.
- Each sampled case made two OpenRouter generations. The requested `:free` candidate generation had `total_cost: 0`; a separate generation with model `typesafe/jev-1.13-20260917` had `api_type: decisions` and `total_cost: 0.000061404` (1280 prompt and 58 completion tokens). The pilot included this in `costUsd`. We have **not established the purpose or configurability of that second call**. The two pilot invocations (one stopped after a zero-cost assertion failed, one completed) increased `/api/v1/key` usage from $0.344051046 to $0.344296662, exactly $0.000245616, or four such charges. Thus free candidate slugs do not imply a free Ori Eval workflow. `ORI_FALLBACK_MODELS` was explicitly empty; further investigation must distinguish Ori internal evaluation/selection from fallback before claiming either.
- The pilot estimate was $0.000245616 for all four synthetic cases, assuming the sampled cost repeats. It is an estimate, not a cap or a complete quality result. No live Kyber agent or dev cluster was used.

## Proposed opt-in job contract

1. The operator starts a manually triggered CI or local job with a dedicated, provider-capped OpenRouter Secret. Never load credentials from a cloned project's dotenv or persisted Ori login. Set `ORI_FORCE_OPENROUTER_API_KEY=1`, `ORI_DISABLE_UPDATES=1`, `ORI_TELEMETRY=0`, and `ORI_FALLBACK_MODELS=''`. Pin Ori, Bun, fixture revision, candidate model IDs, and selected providers in the run manifest.
2. Use a disposable workspace with a fixture repository containing only approved synthetic or redacted prompts. Run `ori eval --list --allow-no-key`, then a `--dry-run --hermetic --no-history` import check, then a one-case-per-model pilot. Use an explicitly empty or reviewed `--features` directory. Inspect the context inventory Ori prints before model calls. Wrap **every** case list with `pilotCases`; a helper or second unwrapped list can escape the pilot guard.
3. Before a full run, confirm the account's enforced key/workspace limit and pilot's actual usage through OpenRouter generation records. Bound wall time, process concurrency, cases, turns, models, and token budgets. Do not rely on Ori's pilot estimate or matchers as an authorization ceiling. Stop on unknown extra models, unexpected provider routing, failed assertions, or a cost deviation.
4. Export a small report with fixture revision, candidate IDs, Ori version, case counts, pass/fail, duration distribution, OpenRouter billed cost, and a clear distinction between candidate and ancillary generations. Do not store raw prompts, completions, secrets, or Ori history in a public PR artifact. Retain only approved aggregate results; delete the temporary workspace and logs after reporting. Explain that the result screens models and is not evidence of Kyber's agent behavior.

## MAT-110 boundary and follow-up

Revise MAT-110 to a documented opt-in job only if Matt wants this screening workflow. Do not implement a console/API/CRD eval launch until there is an explicit product need, a privacy/retention design, spend controls, and a tested Kyber runtime path. Before scheduling a full comparison, determine what triggers the ancillary `typesafe/jev` request and whether it can be pinned, disabled, or budgeted. Re-run both coding and noncoding cases under a capped key; compare the same candidate slate, record provider generation IDs privately, and review any model or cost drift. A separate live Kyber canary is required to claim harness or channel compatibility.

## Review notes

The first draft risked interpreting the pilot's positive `costUsd` as a paid candidate or billing estimator. Generation records and key-usage delta show an actual ancillary paid request. The product wording and cost gate above reflect that correction. The two passing sampled coding cases are deliberately not reported as a quality comparison.
